# woody-woodpacker

A naive ELF64 packer built for the 42 school curriculum. woody-woodpacker takes a statically linked ELF64 executable, encrypts its `.text` segment, and injects a small decryption stub that runs at program start, decrypts the code in place, and hands control back to the original entry point.

## How it works

1. **Parse the target ELF**. Read the ELF header, program headers, and locate the executable PT_LOAD segment (the one containing `.text`).
2. **Encrypt `.text`**. The executable segment's bytes are encrypted in place using a stream cipher (RC4) with a randomly generated key.
3. **Write and inject a stub**. A small, self-contained x86-64 assembly stub is written into the binary (naive code cave implementation). The stub:
	- calls mprotect to make the encrypted segment writable,
	- runs RC4 key-scheduling and decrypts `.text` in place,
	- jumps to the original entry point.  
4. **Redirect e_entry.** The ELF header's entry point is rewritten to point at the stub. The stub itself stores the original entry point and jumps to it once decryption is complete.

## Usage

```bash
	./woody_woodpacker <path-to-executable>
```

On success, a packed binary named woody is created in the current directory.

## Scope and limitations

### Dynamically linked binaries

woody-woodpacker refuses to pack any binary containing a `PT_INTERP` segment (i.e. any dynamically linked executable). This is a deliberate design decision, not a missing feature — see below.

### Why dynamic linking is unsupported

During testing, packing certain dynamically linked binaries (e.g. gdb, rsync) produced binaries that crashed with a SIGSEGV before the stub ever ran, affecting a small but real fraction of test cases (>1% of the test corpus).

The root cause in every case was the same: the dynamic linker (`ld.so`) is invoked by the kernel before the packed binary's own entry point runs, whenever a `PT_INTERP` segment is present. `ld.so` performs relocation processing as part of its own startup — entirely outside the packed binary's control — and this processing can require reading from or executing code inside `.text`, which at that point is still ciphertext. The stub's entry-point redirection trick offers no protection here, because the stub never gets a chance to run before `ld.so` does.

Two distinct relocation mechanisms were identified as concretely triggering this:

- **Symbol interposition**. When a binary statically links a language runtime (e.g. libstdc++) and does not hide the runtime's symbols (e.g. operator new / operator delete), those symbols become globally visible exports of the packed binary itself. If a needed shared library independently references a symbol with the same name, the dynamic linker's symbol resolution rules give the main executable priority — so the library's call gets resolved against the packed binary's own (still-encrypted) definition. Under BIND_NOW, this resolution happens eagerly, before the stub runs, and the resolved address points into ciphertext.
- **IRELATIVE relocations**. R_X86_64_IRELATIVE relocations do not store a fixed address — they store the address of a resolver function, which `ld.so` calls directly during relocation processing to determine the real target address (used for glibc's IFUNC/CPU-feature-dispatch mechanism). If the resolver function lives inside `.text`, `ld.so` jumps into and attempts to execute ciphertext directly, which the CPU decodes as garbage instructions, causing an immediate crash.

Refusing any binary with a `PT_INTERP` segment eliminates both failure modes at the root: with no `PT_INTERP`, the kernel jumps straight to the packed binary's own e_entry — the stub — with no external program (`ld.so`) ever getting control first. This guarantees `.text` is fully decrypted before any code, static self-relocation logic included, has a chance to execute.

## Testing

A test suite (`tests/`) runs the packer against a corpus of statically linked binaries, comparing the packed binary's behavior against the original for a set of invocations, and logging any creation or execution failures for inspection (at path `./tests/logs`).

Run the test suite with:

```bash
	# at the repository root
	bash ./tests/tesh.sh
```
